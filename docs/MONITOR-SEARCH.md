# Search when Sonarr monitoring is enabled

Guided **step 3** automatically installs a separate Sonarr monitoring-change
companion after the media applications' accounts and connections pass. No
additional account, browser wizard or prompt is needed. The companion uses the
existing private Sonarr key; it does not create users or change profiles.

On first activation it records the current missing episodes as a **baseline**.
It submits no search for that existing backlog. Later observations check about
every 30 seconds for an already-known episode whose effective monitoring changes
from off to on. Series, season and episode monitoring all contribute to that
decision. The episode must be aired, missing and still monitored when dispatched.
Episodes newly observed by this companion are baselined, not bulk-searched.

A qualifying transition submits Sonarr's native `EpisodeSearch` command for the
explicit episode IDs. The existing quality/language profiles, sources and download
clients still decide whether any release can be acquired. Monitoring is an intent
to search, not proof that a suitable release exists or a file has downloaded.
Seerr's own search remains native; the companion checks queued downloads, active
searches and recent episode searches to avoid duplicate work.

## Bounds and durable state

- Each poll searches at most two shows, with at most 24 episodes per show.
  Additional observed transitions remain pending for subsequent polls.
- Durable command claims also bound dispatch to 120 episodes per hour and
  500 per day. Repeated toggling cannot bypass those episode budgets.
- Existing episode files and unaired episodes are excluded. This is not a
  recurring Wanted/Missing backlog search or an automatic quality upgrade.
- Private pending transitions and command claims survive reboot, source-folder
  replacement and ordinary poll failures. Already submitted commands are not
  automatically resent after an ambiguous response; inspect Sonarr's commands
  before any deliberate retry.
- Every dispatch rechecks the owned container, its pinned image and persistent
  application directory, the intended media mount and the 50 GiB media / 20 GiB
  application free-space floors. A failed check prevents dispatch; it does not
  delete files, resume downloads or bypass VPN/storage policies.
- It never renames, imports or deletes media, changes account/settings policy,
  or starts a stopped media application.

Keep `install_root/state/sonarr-monitor-state.json`. Deleting it discards event
history and makes the next observation a new baseline; it is not a repair step.
Do not edit this file or copy it between installations.

## Apply only this companion to an existing installation

New and resumed guided step 3 handles it automatically. To install or update
only the companion, use the current release's Bash `stack` entry point from the
media VM, with the installation's existing private site configuration:

```sh
sudo ./stack --config /path/to/existing/site.json monitor-search install
sudo ./stack --config /path/to/existing/site.json monitor-search verify
```

Replace only the example configuration path. Preserve the original deployment
identity, application directories, media mount, secrets and monitor state. This
maintenance action does not apply Compose, restart media apps, change their
connections or search the existing backlog. It runs an initial baseline only
when state is absent, then runs the companion once in its actual systemd sandbox
before enabling its timer. Valid pending user changes may be processed by that
normal guarded poll. `verify` is read-only and never invokes a search poll.

The timer is `samurai-DEPLOYMENT-sonarr-monitor-search.timer`; its matching
oneshot service has the same name ending in `.service`. `DEPLOYMENT` is the
saved `deployment_name`, not the friendly Compose project name. Both units carry
the installation UUID. The copied standalone worker and private policy live
under `install_root`, so moving or replacing the source checkout does not stop it.

Known owned artifacts can be updated with private before-copies. Foreign units,
systemd overrides, mismatched ownership and locally edited scripts block
replacement. Existing event state is never reset to make installation succeed.

## Check it without searching a library

For a deployment named `homelab`, read the companion's status and journal:

```sh
sudo systemctl status samurai-homelab-sonarr-monitor-search.timer
sudo systemctl show samurai-homelab-sonarr-monitor-search.service \
  --property=Result --property=ExecMainStatus
sudo journalctl -u samurai-homelab-sonarr-monitor-search.service -n 30 --no-pager
```

Use your actual deployment name. The oneshot service is normally **inactive**
between successful polls; the timer should be enabled and active. A successful
baseline alone is insufficient: installation also requires a real successful
service poll. `monitor-search verify` checks its last process result and the
enabled timer without submitting commands.

To accept the feature, choose one missing, aired episode you are authorized to
download. Let the running companion observe it unmonitored, then enable its
monitoring and wait for a poll. Inspect Sonarr's Activity/History and native
command result. A search with zero releases is different from no search.
Do not toggle a whole existing library merely to test the helper.

If an episode was already monitored when first baselined, use Sonarr's own
deliberate search for that episode, or intentionally disable and re-enable its
monitoring with enough time for an off-state observation between those actions.
A rapid off/on toggle entirely between polls cannot be observed by polling.
